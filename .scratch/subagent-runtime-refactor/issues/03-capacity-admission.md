# 03: 并发名额满时明确拒绝派工

**What to build:** 用户能预测同时运行的子任务数量；容量不足时获得明确反馈，没有隐藏排队或等待名额消耗整任务超时的问题。

**Blocked by:** 02：异步派工并查看独立子任务

**Status:** implemented — 依据后续 `implement` 指令实施；验证结论及未验证范围见 [验收报告](../acceptance.md)。

**Spec acceptance:** A23, A24。部分覆盖的边界以各验收条目和总览映射为准。

依据：[定稿规格](../../../docs/prd/subagent-runtime-refactor-spec.md)、[ADR-0005](../../../docs/adr/0005-subagents-retain-identity-across-tasks.md)、[领域术语](../../../CONTEXT.md)。

## Acceptance criteria

以下保留原验收清单；逐项证据统一记录在验收报告中，未做实际 provider 端到端验证的条目不据此宣称实测通过。

- [ ] A23：应用进程内原子预留活跃子执行名额，默认 12、范围 1—64，不含主代理；并发启动不超额。
- [ ] A23：受理失败、准备失败、panic、取消和清理完成均正确释放名额；仍在清理的任务不提前释放，空闲历史不占名额。
- [ ] A24：满额请求明确拒绝，不留下幽灵任务或隐式队列；可在其他任务结束后重试，受理键保持幂等。
- [ ] A24：调低上限不强杀已有执行，新任务按实际容量受理；UI 与模型回执展示同一容量原因。
- [ ] A24：去掉覆盖整个子任务的固定 660 秒期限，保留模型、工具及轮次限制；用可控时间验证长任务不因旧总期限结束。

## Verification

限额设为两个，启动两个任务后第三个被拒绝；一个完成后重试成功。

通过用户与模型共享控制接口检验可观察行为；涉及 UI 的行为须有操作验证，涉及持久化的行为须用真实存储验证。只实现本项明确范围，公共行为遵循规格，不能用临时实现替换既定承诺。
