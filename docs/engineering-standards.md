# Kivio 统一工程规范：短流程、单一归属、小接口

本规范约束后续新增、修复和重构。目标是让一次用户操作走最短的正确路径，让同一规则只改一处，而不是让目录、文件或类看起来整齐。

这是工程简化规则的唯一维护入口。历史架构规格记录迁移目标和验收；其中的 controller、owner、公开入口不是每个功能必须凑齐的层次。已有产品不变量、领域 ADR、安全检查和数据兼容要求继续有效；若简化方案与它们冲突，先明确冲突并取得决定，不能静默覆盖。

## 1. 先找归属，再决定是否拆分

- 一个业务规则只有一个权威实现；一份可变状态只有一个写入负责人。按业务能力和生命周期归类，不按 Controller / Service / Manager 名称建立套娃目录。
- 先修改已有 Module（带 Interface 和 Implementation 的功能单元）。Interface 包括操作、结果、错误和生命周期约定；调用方不应了解内部执行顺序。
- 单一页面的展示状态、局部事件处理和只在附近使用的纯函数可以留在原文件。文件变长是调查线索，不是拆分理由；也不把不同生命周期硬塞回一个大文件。
- 共享代码在确有多个调用方使用同一规则时提取；领域专属逻辑留在所属目录，不能仅因两个页面调用就搬进 `utils`。

### UI 必须优先复用全局实现

- 新增或重做页面前，先查找已有全局组件、样式和主题 token。有全局实现就使用全局实现：动作按钮用 `src/components/Button.tsx` 的 `Button` / `IconButton`，输入与选择控件通过 `src/settings/public/controls.ts` 复用，滚动容器使用 `custom-scrollbar`，弹窗复用 `kv-modal`，颜色、字体和动效使用全局语义 token。
- 引用了共享组件后，不得再用页面 CSS 覆盖其尺寸、颜色、边框、圆角、悬停、聚焦或禁用状态；使用组件现有的属性和变体。页面样式只负责业务内容与布局，不复制一套基础控件或明暗主题。共享能力有缺口时，在原负责人中补齐并验证原调用方。
- 验收时逐项检查滚动容器、按钮、输入框、下拉菜单、弹窗以及主题切换；仅引用了组件但仍局部覆盖基础样式，不算完成复用。不要在页面写 `scrollbar-width` / `scrollbar-color`，它们会覆盖全局胶囊滚动条。

## 2. 默认调用路径

以下是职责路径，不是必须建立的目录、类或固定函数层数：

核心验收是**变更局部性**：改一个动作的规则，通常能定位到一个负责该动作的 Module，必要时再改它直接协作的 Interface；不是沿途修改每一个转发点。“一两处”是维护体验的目标，不是强制所有操作最多两次函数调用。真实的跨端契约或产品变化可以涉及更多位置，但须说明各处为何必需。

同一动作来自按钮、快捷键或其他窗口时，应汇入同一个业务入口。入口里能读出主要步骤、分支和失败处理；底层的计算、存储、协议和平台细节由内部 Implementation 隐藏。调用方只需知道输入、结果及生命周期约定，不必替它组装执行步骤。

命名优先说明动作和业务对象；相关规则与行为测试就近放置。一个新维护者应能回答“从哪里进入、谁做决定、状态归谁、改规则改哪里”，而不是先遍历整张依赖图。若必须修改多个无关目录才能改变一个局部规则，先检查职责是否分散，而不是继续加一层入口掩盖它。

| 操作 | 默认路径 | 何时增加编排 |
|---|---|---|
| 局部展示、计算 | 页面 → 局部状态或纯函数 | 不需要业务编排 |
| 简单读取或独立命令 | 页面/现有 hook → 已有带类型的命令 Adapter → Rust 所属 Module | 只有出现真实的业务顺序或资源生命周期才增加 |
| 设置编辑、导航、发送等有状态流程 | 页面意图 → 已有流程负责人 → 所需命令或领域能力 | 同一个用例只由一个入口决定步骤、失败和结束条件 |
| 跨领域协作 | 已有应用组合入口 → 各领域公开 Interface | 组合入口管协作顺序，各领域仍管自己的状态 |

页面只绑定意图和展示，不补齐领域清理顺序。简单读取可以直接走已有 Adapter；设置写入、导航提交、发送占位等受保护操作必须走已有负责人，不能借“直达”建立旁路。前端不在页面里新增裸 `invoke` 或另一套协议解码。

同一领域内部允许直接调用内部函数；跨领域使用声明的公开 Interface。目录归属和允许的依赖以 `architecture-boundaries.json` 及现有检查器为准，不能靠移动分组逃避检查。

## 3. 新增抽象必须有收益

增加 Module 或包装层之前，必须能说明以下至少一种收益，并在变更说明中用一句话给出证据：

- 收拢一个完整状态生命周期或业务不变量，让调用方不再自行协调。
- 消除多个真实调用方的重复规则。
- 在确实变化的 Seam（可替换位置）隔离不同 Implementation，例如操作系统、CLI 协议或外部 I/O；测试替身也应对应真实的外部依赖。

仅改名、原样转发参数、把同一组 setter/ref 搬到另一个文件，不能成为新增层的理由。做一次“删除测试”：去掉该层后，如果规则和生命周期没有重新散落到调用方，优先合并它。

必要的轻量 Adapter 可以保留：IPC 解码、协议转换、React 订阅与释放、兼容旧契约。它们只做该项适配，不复制业务决策。仅声明导出范围的 `public/*` 再导出也可保留；它不是新增运行时调用层，不必再给它包一层函数。

一个已有流程负责人可以直接组合私有函数；只有真正独立的生命周期才拥有另一个负责人。不能为“以后可能替换”预建通用框架、工厂或多级转发链。

## 4. 状态和规则只维护一次

- 调用方读取快照、提交意图，不接管裸 map、锁或整组 setter。可派生的值按需计算，不靠多个 effect 互相同步副本。
- 必需的副本必须说明语义：例如后端规范设置、已确认编辑基线、未保存草稿各有用途，不应为了字段少而混为一份；缓存必须有明确的更新与失效负责人。
- 持久设置的默认值、迁移和规范化归后端；前端校验用于输入反馈，不能成为另一套权威规则。共享协议使用现有生成契约。
- 锁、CAS、原子文件替换、权限检查、取消及迟到结果隔离是正确性约束，不是应删除的“多余层”。简化应隐藏其使用细节，而非移除保护。

## 5. 流程必须能直读

- 每个用例从一个入口读出正常路径及失败路径。调用方不需要依赖多个 hook 的执行顺序、跨 hook 回填 ref 或事件接力才能完成一次本地操作。
- 同一操作的业务重试、去重和终态由流程负责人决定；传输重试只处理明确可重试且安全的传输错误，次数有界，避免上下层叠乘。
- 需要返回结果的同进程调用使用直接函数和返回值；跨窗口通知、流式输出、进程交互使用事件或 channel。通知表达已发生的变化，不成为第二条隐式写入路径。
- Interface 说明成功、失败、冲突和取消的可观察结果。保存失败不能表现为成功；隐藏、卸载、关闭和停止后台任务分别按既有产品语义处理。
- 异步完成只更新仍属于该请求/导航/会话的状态；清理由持有资源的 Module 负责。正常页面跳转不依赖调用方手动重置另一领域的内部字段。

## 6. 高效：不让无关工作阻塞主流程

- 等待只用于保证该操作的正确性；无关的刷新、探测、统计和预加载不成为必经前置条件。独立任务可并行，需要顺序的提交仍顺序执行。
- 缓存刷新、订阅和定时器在所属 Module 内复用；一次变化只更新受影响的数据，不在每层各做一次全量刷新。
- 流式输出、列表滚动和输入等高频路径保持局部更新。新增缓存、批处理或异步调度须有重复工作或性能测量依据，不能仅凭“可能更快”。
- 行为简化比较用户步骤、等待项和调用路径；性能改善比较同场景测量结果。少几个文件或一次测试更快，不等于应用更快。

## 7. 修改和验收保持轻量

普通修复不需要额外设计文档。新增流程或改动归属时，在任务说明/PR 中给出“原路径 → 新路径、唯一负责人、删除了什么、如何验证”；需要例外时就地说明原因和移除条件，不新建一套审批流程。

每次审查回答以下问题：

1. 不沿调用链逐层追踪，能否定位该动作的负责人和修改位置？同一动作的不同触发入口是否共用规则？
2. 状态和规则是否仍只有一个权威？新层是否通过删除测试？
3. 一次局部规则修改是否仍牵动无关 Module？是否移除了已迁移的旧入口和重复逻辑，而不是新旧两套并存？
4. 是否增加了与目标无关的等待、请求、刷新或用户步骤？
5. 是否通过真实调用 Interface 验证结果，而不只是断言中间函数被调用？

缺陷修复先建立能失败的回归用例。涉及流程时，按影响覆盖正常、失败、重试、并发/迟到结果、离开重开；验证最终快照、持久化结果和资源清理。保留有价值的纯函数测试，不机械复制每一层的相同断言。

验证命令读取 `package.json` 和现有项目指导，复用现有类型、Lint、协议、架构及测试检查。当前架构检查能拦依赖违规，不能证明流程简洁；上述语义问题由审查确认，不声称已经自动化。涉及桌面流程的变更还需实机验证，未执行必须明示；纯文档变更检查链接、冲突和差异即可。

## 8. 存量代码按流程逐步收敛

本规范生效不等于全仓已符合。只整理当前任务涉及的流程：先固定行为，再合并无收益的转发、收回重复状态，迁移调用方后删除旧路径。每批保持可验证，不为贯彻规范再发动一轮无差别拆分或大规模改名。

完成标准是调用方需要知道的事情更少、修改更局部、行为验证通过；不是 controller 更多、文件更短或抽象名称更统一。

## 依据与适用范围

上述变更局部性要求是本项目对公开工程原则的应用，不是任何公司的“最多两层”标准。Google 强调可直接阅读、避免无收益抽象；Android 官方明确可选业务层不应退化为强制转发；Microsoft 强调通过封装隔离内部变化。资料原意、来源及适用限制见[架构简化资料核验](research/architecture-simplicity-2026-09-19.md)。该笔记只记录依据，不另立规范，也不要求本桌面项目采用 Android、.NET 或微服务架构。
