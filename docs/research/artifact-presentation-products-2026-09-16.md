# 产物展示研究：Codex、Claude、Gemini 与 Kivio 的改进方向

> 时效说明（2026-09-20）：本文保留 9 月 16 日的调查及实施历史。Claude 关于作品入库和分享的新旧体验差异已在[后续调研](claude-artifacts-2026-09-20.md)更新；下文“聊天作品须 Publish 才进入集合”仅适用于官方所述旧 Chat 体验，不再作为所有当前 Claude 体验的结论。

核对日期：2026-09-16。范围：官方产品帮助中可核实的产物入口、正文关系与版本管理，以及 Kivio 本地实现。本轮只研究，不修改应用代码；调查时工作区已有上一轮尚未提交的产物时间顺序修复。

## 结论

对 Kivio 的建议是：**中间产物默认留在过程里，最终答复按内容需要引用必要产物；不要把所有曾生成的文件自动提升为交付结果。**

这是一项产品建议，不是已经证实其他产品完全采取同一策略。下列官方资料支持“产物有独立身份、可持续更新、可以与聊天分离”的设计；并未公开所有中间文件的筛选算法。

## Kivio 当前实现：已查到的事实

1. **已存在“登记不等于展示”的基础。** 新的带 ID 文件不会自动进入回答末尾画廊。模型需用 `present_artifacts` 选择展示；旧的无 ID 文件仍有自动展示兼容逻辑。因此不能把当前问题描述成“所有生成文件都会自动展示”。见 [MessageBubble.tsx](../../src/chat/MessageBubble.tsx)、[artifactPresentation.ts](../../src/chat/artifactPresentation.ts)。
2. **展示调用没有用途和正文位置。** 现有参数只有 `artifact_ids`、`paths` 和 `caption`；一次调用对应时间线中的一张展示卡，没有“过程检查 / 中途预览 / 最终交付”的语义，也没有最终正文段落锚点。见 [工具定义](../../src-tauri/src/mcp/types.rs)、[工具执行](../../src-tauri/src/mcp/native_registry.rs)。
3. **提示词强调展示，但缺少筛选标准。** 系统提示要求在展示点调用 `present_artifacts`；工具结果提示虽说文件不自动显示，其示例却填入了该次结果的全部 ID。“这可能诱导模型一次展示全部”是实现推断，尚未通过模型对照实验确认。见 [prepare.rs](../../src-tauri/src/chat/agent/prepare.rs)、[artifact_presentation_hint](../../src-tauri/src/chat/agent/execute.rs)。
4. **正文内嵌已有部分能力。** Markdown 图片可按文件名查找 artifact；一般文件是可打开的本地链接。但图片文件名冲突保留第一张，尚无统一按稳定 ID 引用图片、视频及文档卡的正文机制。不能直接把现有文件名匹配当成可靠的最终交付协议。见 [ChatMarkdown.tsx](../../src/chat/ChatMarkdown.tsx)、[文件卡](../../src/chat/GeneratedFileArtifacts.tsx)。
5. **上一轮修复处理了次序，没有解决选择。** 当前未提交修改让展示卡前后的过程保持时间顺序，共用一个 Work 开关；它没有判断哪些文件值得展示。后续明确请求的中途预览仍需要这个顺序保证。

因此推荐同时完善展示策略和正文引用能力。只把所有展示卡挪到结束时一起显示，仍然会留下数量过多、重复展示、和说明脱节的问题。

## Kivio 的建议契约（设计建议）

### 1. 生成、预览、交付分开

文件产生时登记它，但不因此自动放到结果区。诊断截图、抽帧、转换文件及草稿默认归过程，用户展开过程仍能找到。最终答复需要哪个文件，就在相应段落引用哪个文件。

确实需要用户中途选择的预览可提前展示，例如让用户选择两个设计稿；这种预览有明确目的，不能只因为图片已经生成便展示。本文不建议第一版就加入新的侧栏产品。

### 2. 正文控制位置，应用保证可用

最终答复应能表达：结论 → 必要证据图 → 操作说明 → 可下载文件。应用在引用位置呈现图片或文件卡，避免把产物统一堆在正文顶部/底部。

提示词负责要求模型挑选结果并解释用途；应用负责解析引用、核实文件存在、消除同一引用的重复卡片、处理失效引用。只改提示词不足以保证布局和可用性。

### 3. 同一结果保留身份

文档更新不应表现成十张同级最终卡片。可为同一结果保存稳定标识及版本，默认展示最终答复引用的版本；历史版本仍可追溯。不同文件是否是同一产物，应由明确关系决定，不要仅靠相似文件名猜测。

### 4. 失败和旧记录不能直接丢

运行中断时，没有最终引用的文件仍在过程内可取用，不能把它们冒称完成交付。历史记录没有正文引用时需保留兼容入口；新策略不应让旧对话已有下载链接消失。

### 5. 对用户截图的具体落点

截图里的逐帧抽样应先视作测试证据，放在过程。最终如果确实需要展示“操作前/后”的变化，可在介绍测试结果的那一段放两张已选截图；录像则在说明可观看演示的位置放一次。不要把所有抽帧和每次录制尝试全部放进最终答案。

## 后续实现前要确认的验收项

- 连续产生多张过程截图，最终只引用一张：结果区只出现该张，其他仍可在过程找到。
- 同一文件多次更新：最终卡片打开的内容与引用版本一致，旧版本有追溯方式。
- 两个文件在不同段落引用：各自出现在对应段落，不额外生成头部总附件区。
- 最终引用不存在或格式错误：有可理解的失效状态，不静默吞掉交付物。
- 停止、错误、切换任务、刷新后：文件可访问性和正文顺序一致。

以上是下一步实现建议，不代表本轮已修改或验证 Kivio 的行为。

## 推荐实施顺序

第一阶段实现默认行为与可靠引用，不先做一个完整的产物管理平台：

1. 明确策略：模型自检截图、抽帧、格式转换和失败尝试默认留在过程；只有用户请求预览、需要用户做选择，或有明确阶段性交付需求时才提前展开。
2. 最终正文使用稳定 ID 引用所选产物。具体语法实施时再定；必须复用已登记的文件，应用负责在引用处渲染图片/文件卡并验证 ID，不靠模型编造文件名或前端猜测“最后一张就是最终稿”。外部 CLI 的普通路径链接继续兼容。
3. 文件登记、预览事件、最终正文引用分别保存。一个文件可以先预览、后交付；不把它永久分类为“中间文件”。默认不要额外在答案顶部或底部重复汇总已经内嵌的文件。
4. 对显式交付却缺少正文引用的记录提供紧凑的可打开入口；未知用途的过程文件不能借兜底规则全部进入结果区。引用失效时给出可理解的状态，不能静默吞掉用户所需文件。
5. 历史记录、取消和报错不强行重写为成功交付。无最终答复时文件仍可在过程里找到；完成状态与文件是否存在分别处理。

第二阶段再考虑同一文档的版本切换、侧栏文件集合和可视化批注。第一阶段的验收重点是“用户无需翻过程就能拿到需要的结果，同时过程不会被中间文件刷屏”。

### 用这次浏览器测试举例

运行时只播报测试进度，抽帧图默认留在过程。最终答复可这样组织：

> 实测完成，10 项能力通过。
>
> 验证了输入、提交和页面状态变化。
>
> （只有确实帮助理解结论时，在这里放所选的前后对比图）
>
> 录制了完整操作过程，可打开演示录像。
>
> （这里放 demo.mp4 卡片）
>
> 其余测试结果与必要使用说明。

若用户只需要“能否使用”的结论，正文可以仅保留结果和一个可选录像入口，不必为了展示而加入对比图。以上示例中的文件名来自用户截图，仅说明排版建议，不构成新的测试结论。

## 第一阶段实施（2026-09-16）

用户随后授权先提交时间顺序修复，再实施本研究建议。上一轮顺序修复已提交为 `73a70f54`；本节描述后续实现。

- 新的 `present_artifacts` 默认 `mode: prepare`，只为选定交付文件准备引用，过程里显示可展开的紧凑文件记录。`mode: preview` 用于用户明确要求的即时预览或中途选择。缺少 mode 的历史记录保持原展示方式。
- 最终正文可用 `[说明](artifact:art_ID)` 放文件卡，用 `![说明](artifact:art_ID)` 放图片；只解析当前消息实际拥有的 ID。保留现有本地路径链接，缺失 ID 显示不可用提示。
- 已在正文引用的文件不再重复出现在独立预览区；重复预览调用也按 ID 去重。已明确 prepare、但最终未引用的文件，在正常结束后提供紧凑兜底入口；未选择的普通中间文件不因此进入结果区。停止/错误时仍可展开过程取用已准备文件。
- 修复了 Markdown 分块缓存导致“文件晚于正文到达后仍显示不可用”的问题：文件引用通过上下文原位更新，不重挂载整个答案。引用式 Markdown 的定义也会转换为块内文件引用，避免跨块定义失效。
- 更新系统提示、工具说明和文件返回提示：默认不展示内部验收截图、抽帧、草稿与失败尝试，按最终说明选择必要文件；不再给出将所有可用 ID 一次展示的示例。
- 验证覆盖运行到结束、手动折叠、重载、取消/报错、缺失文件、文件晚到、同名不同 ID、代码示例、预览去重和引用式链接。真实浏览器使用实际 MessageBubble 组件与固定测试数据检查了运行中及完成布局，截图保存在本地 `output/playwright/artifact-running.png` 和 `artifact-final.png`。这不是实际模型生成的端到端调用。

版本管理与侧栏文件集合仍属于第二阶段；本轮未实施，也未承诺模型在所有任务中都能完美挑选交付物。
