官方产品开源项目源码发现对 Kivio 的启示核验方法

1. 官方 Grok Bot 的产品边界

已核对 官方产品页、发布公告和官方文档。名称确为 Grok Bot，发布于 2026-08-11。它的核心是具名、具职责、能持续工作的 AI 同事。用户参考图的联系人列表，与官网渲染演示的 Chief、Inbox Manager、Expense Manager 等 Bot 列表形态吻合；无法确认参考图的具体版本。

联系人就是工作身份

Bot 有姓名、职责、头像、自己的聊天及持续工作上下文。点联系人直接续聊，长期职责写入 Profile，具体任务通过消息交代。官方 Bot 管理

聊天承载工作过程

时间线显示普通消息、工具活动、电脑操作、生成文件、问题、审批和语音。运行中可补充指令；Bot 间异步交接会唤醒接收方。聊天与协作

记忆与例行工作持续归属于 Bot

每 Bot 保留稳定偏好、事实和工作摘要。Routine 由某个 Bot 持有，在时间或事件触发后工作并回到它的对话。记忆边界 · Skills / Routines

执行环境可以共享

官方是账号共享一台云电脑，每 Bot 独立 screen。文件、浏览器登录和命令行凭据共享；screen 不是权限隔离。云端工作不依赖用户电脑保持打开。电脑与应用

联系人列表还有 working/typing、unread、needs attention 三类状态；隐藏 Bot 只移出侧栏，不停掉其工作和 routines。复制 Bot 携带配置，不复制历史与学到的记忆。状态与通知 · 管理语义

以上能力来自官方文档。官网界面由子代理在后台浏览器观察；它是演示原型，不是登录真实账号后的执行验收。官方底层存储、压缩和调度实现未找到可核验完整源码。团队 Bot、群聊与 Slack 支持额外会话关系；本次目标聚焦个人 Bot 的固定私聊。Team Bot 文档

3. 源码中值得借鉴的区别

Bot 身份、持续消息记录与一次运行分开

Rakazo 的 Thread.botId @unique 和 Bot.thread 约束一个 Bot 至多一条直接私聊。任务和 Run 有自己的 queued/running/waiting/completed/failed 状态，结果回到持续时间线；群聊和外部渠道会话另存。这与本次“一 Bot 一长期聊天”吻合，并不需要在联系人下面展示任务目录。源代码

BOTROSTER 把 profile 放在 bot.json，消息放在 conversation.jsonl，交接放在 inbox.jsonl。重命名不更改稳定 Bot ID；每次 system prompt 重新带入 standing brief。但 inbox 的消费目前只在 CLI run --bot，桌面与 routine 的 run_task 未接通接收；不能把投递成功当完整转交。BotStore

长期聊天可以完整保存，请求上下文仍然有限

Rakazo 当前默认 retrieval，保留原始消息并通过 read_history/search_history 检索；只有 current 策略才安排后台摘要压缩。该压缩分支检查摘要覆盖位置和后续消息的连续序号，避免中间漏一段。请求侧依据模型预算、输出预留和工具结果体积选择内容，原始产品历史仍保存在数据库。其底层 Pi 日志只是可选运行记录。历史压缩 · 请求上下文 · Pi 日志

OpenMausBot 的重建流程保留摘要、近期交流及最新纠正、取消和已完成工作的状态；摘要失败还有带来源的文本片段回退。OpenGrokBot 则简单取最近 40 条消息，不能把这种截断当作完整的 token 预算压缩。上下文重建 · 摘要 · 最近消息策略

长期记忆独立于聊天摘要

Rakazo 区分 Bot memory 与 user memory，在请求中以有限预算注入，并明确它们可能过时。OpenMausBot 把记忆做成可检查、可编辑、可删除的文档，写入使用 expected hash 检查，避免覆盖用户刚编辑的内容。OpenBot 将稳定 Bot 知识与 thread 的临时任务状态分开。Rakazo memory context · OpenMausBot memory store · OpenBot memory

BOTROSTER 已核实 standing brief 和持久历史；没有核实独立语义记忆/提取层。OpenGrokBot 的记忆是每员工 Markdown，后台重写、失败为 best effort。SDK 读取真实 host 的 profile 与按月日志，只能证明记忆与 transcript 分开，不能证明官方如何压缩。OpenGrokBot memory · SDK disk memory

换模型与编辑 Bot 时，产品身份可以持续

模型 session 是运行时状态。OpenGrokBot 在同一 Conversation 中按员工和 provider kind 分别保存 session；更换 provider 或 cursor 丢失可重新建立它。已有 Codex session 只增量发送近期 transcript，persona/notes 在新 session 首次注入，故编辑人格后未必每轮更新；这是不能直接照搬的限制。Session 维护 · Codex provider

Rakazo 每次 worker 执行读取 Bot 配置，但显式 pinned model 的 Run 保留创建时模型。OpenMausBot 的 bot 默认模型、thread override、运行中的选择有明确生效规则。Kivio 将来应说明改动影响下一次工作还是当前执行，而不是把“配置已保存”当作“运行中的模型已经换了”。Rakazo model selection · OpenMausBot 生效语义

持久同事与临时子代理分别管理

Rakazo 将持久 peer Bot 与 turn 内临时 subagent 区分：peer 有名字、自己的私聊和持续职责，临时助手处理当前工作分支。这让一次并行调研不会把联系人列表堆成一批临时 Bot。Child bots

电脑、文件、浏览器和登录的共享必须单独看。Rakazo 有 Team Computer / Private Computer 两种，官方 Grok Bot 则默认账号共享电脑。OpenClaw 可以补充 agent/workspace/auth/session 的隔离概念，但它是邻近生态，不是本次直接衍生。Rakazo 电脑边界 · OpenClaw 多 Agent

4. 对 Kivio 产品讨论的启示

界面直接呈现 Bot 联系人；内部保留历史、上下文和运行边界。下列是研究推断，不是这轮实施决定。
  1. Bot 应有自己的持久身份。名字、头像、职责、模型偏好、授权工具、工作环境和长期记忆，围绕这个身份存在。现有助手配置可以作为创建 Bot 的起点；把所有“常用助手”直接自动变成 Bot 仍需产品决定。
  2. 一个 Bot 的私聊始终可继续。上下文压缩、模型切换和运行重建不迫使用户创建新联系人或进入另一个对话层次。每次工作仍有自己的状态和记录。
  3. 联系人列表应展示关系与状态。名字、最新消息、时间、工作中、未读、需要处理，是参考图与官方产品最直接的共识。隐藏、停止、删除分别表达不同动作。
  4. 长期规则、记忆、一次任务各有用途。职责/指令定义长期工作方式，记忆保存可核对的偏好与事实，聊天消息交代具体任务。用户应能检查并修正记忆。
  5. 定时和协作回到所属 Bot。Routine、任务交接和子任务结果可在私聊里形成持续工作关系，不能让后台执行的身份和用户看到的名字脱节。
  6. 已有两种列表继续保留。这是本次对话已确认的产品边界。Bot 作为第三种入口时，旧聊天是否手动升级、升级到哪位 Bot、原有项目/集权限如何保留，应等研究讨论完成后再定。

“一 Bot 一条长期聊天”这一目标可以直接成立。现在还需要讨论的，是 Bot 的创建/升级入口、配置和记忆归属、定时工作与持久同事的关系，而不是重新引入联系人下面的对话目录。
