优先处理项

P1 · 确定的协议处理缺口

Pi：handled 输入缺少收尾，可能持续等待

0.99.0 起，prompt / steer / follow_up 成功回执增加 data.disposition。当扩展命令或 input handler 消费输入时，回执为 handled，该输入不启动模型运行，官方明确要求不要等待 agent_settled。

Kivio 的常驻读取循环处理成功 response 后继续等待，没有读取 disposition。唯一特殊路径是 /btw 的 entries 回查；它不能覆盖普通扩展命令和输入处理器。steer / follow_up 同样仅凭 success 就发出已注入事件，无法区分扩展已处理与真正排队。

{"id":1,"type":"response","command":"prompt","success":true,
 "data":{"disposition":"handled"}}

本机 Pi 1.0.0 无模型探针：显式加载只返回 { action: "handled" } 的 input 扩展，8 秒观察窗只收到上面一条 response，无 agent_start、agent_end 或 agent_settled，stderr 为零。随后关闭 stdin，正常退出。真实协议行为已复现；未在 Kivio 原生 UI 中复现转圈，UI 后果由现有读取循环推导。

建议：在现有 Pi RPC 负责人内处理 handled 回执；保留 started / queued 的运行生命周期，并区分输入被扩展消费与真正注入。避免简单把所有成功 response 当轮次结束，因为扩展也可能独立启动工作。

P2 · 新增语义未接

Pi：agent_settled.aborted 未参与终态判定

1.1.0 新增 aborted。当前 mapper 只按事件类型返回 AgentSettled，最后是否取消由 Kivio 自己的 cancel flag 判断。如果是 Pi/扩展侧发起的 abort 而本机 cancel flag 未置位，该读取路径不能据此区分取消与正常完成。普通用户点击停止已有独立路径，不能据此声称所有取消都坏了。

建议：接入这项终态语义，验收宿主取消与 Pi 侧取消两种来源。此项为源码与官方事件定义确认的语义缺口，尚未在 1.1.0 真机复现。
