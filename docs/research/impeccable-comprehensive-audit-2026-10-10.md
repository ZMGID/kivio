# Kivio Desktop 全面体验与设计质量报告

> 日期：2026-10-10（UTC+8）。对象：调查期间的 3.1.1 源码与对应 Vite 界面预览。
> 方法：四路独立领域评估，主进程补查翻译、Lens、官网及文档，再交叉核实源码、浏览器行为与单次 Impeccable detector 结果。
> 本轮只调查和出报告；未修改业务代码，未安装扩展，未发送模型请求，未创建、保存或删除用户内容。
> 补充复查：2026-10-10（UTC+8），仅复核定时任务当前改动。后端数据保护和前端错误透传已改进；A03 标为部分修复，A04 的定时任务空态与 B13 的删除说明仍待收尾。复查证据与边界见第 11 节。
> 原有总分仍是首轮全项目评估，不因局部复查重打总分；问题编号与去重计数保持不变。

## 1. 结论与优先顺序

**不建议推倒重做视觉。Kivio 已有清楚的“安静工作台”骨架，需要优先补齐的是可信状态、风险说明、键盘操作和合法小窗布局。**

系统不是一个没有设计的功能集合：聊天主区的视觉焦点、可展开的复杂能力、真实的项目/工作目录与原生会话语义、草稿生命周期、文件所有权说明，都有产品针对性。问题在于这些正确规则没有稳定地进入每一处界面：有些页面将失败画成空库，将未保存画成已保存，将远程处理写成数据不出本机。

按去重后的问题计，本报告记录 **30 项：P0 0 项、P1 10 项、P2 20 项、P3 0 项**。没有把 detector 的 608 条提示算成 608 个缺陷；也没有把预览缺少 Tauri 当成桌面程序故障。

最优先的五组工作：

1. **纠正承诺与状态**：知识库远程处理说明、笔记保存状态、任务读取失败、列表读取失败与空库混淆。
2. **修复共享无障碍缺口**：必要文字与主按钮对比度、真实未命名控件、鼠标专用展开项、文档站隐藏导航的键盘焦点。
3. **修复聊天小窗**：Dock 与聊天列必须一起参与布局约束，而非各自满足自己的最小宽度。
4. **补齐高风险动作的后果说明**：MCP 配置删除、审批策略、外部 CLI 回溯、删除不同所有者的数据、媒体已提交请求与继续取回结果。
5. **最后做一致性整理**：共享控件覆盖、引导与设置交互差异、官网文档更新。不是先换字体、换品牌色或增加装饰。

### 实现完整性判定

- **产品特征成立**：不是可任意套到另一个后台的通用模板；屏幕工具、工作目录、CLI 会话绑定、工具审批和本地产物构成了具体工作台。
- **质量门槛尚有缺口**：A01–A10 中的承诺、状态和可操作性问题不宜归为视觉润色。
- 本结论不是发布批准、无障碍认证或后端安全审计结论。

## 4. 两类主要用户与认知负担

### 开发者/技术用户

**优势**：运行时、项目、工作目录、审批、工具轨迹、CLI 导入和 Dock 在同一工作台中有实际语义，不只是按钮外观相同。权限菜单已能用 Enter、方向键、Esc 操作。

**红旗**：小窗打开 Dock 后输入列被挤掉；“完全访问”不直接说明自动放行边界；“回到这里”未在操作附近说明磁盘文件不会回退，以及 CLI 原生会话到下一轮才对齐。

### 知识工作者

**优势**：空聊天与输入翻译的主动作容易识别；笔记、知识库、媒体与作品提供从输入到结果的完整领域入口。

**红旗**：私有文档“不出本机”的绝对承诺；笔记已保存状态不可信；读取失败被误读为“我没有这些内容”；屏幕热键引导没有及时连接系统权限前提。

### 键盘/辅助技术用户

**优势**：真实 Tab 有焦点环；部分菜单、共享 dialog、主题图库与搜索已有键盘设计；隐藏的聊天/设置缓存页面已有 `hidden + inert`。

**红旗**：内置技能分组不可键盘展开；若干开关/操作按钮缺少名称；任务切换焦点落到 body；官网文档关闭菜单后，Tab 仍进入屏外导航。

### 认知负担判断（I）

1440px 空聊天仍然围绕一个输入动作，视觉分组与渐进展开总体有效。负担主要来自“运行时 / 模型 / 思考等级 / 审批策略 / Act 模式 / 专家 / 项目 / 多模型”属于不同概念，而相邻工具对新用户不总有足够解释。

不把“超过四个图标”机械判为缺陷。开发者工作台本来有内在复杂度，强行收起所有专业能力会损害效率。应减少的是额外解释成本：在审批、工作目录、数据处理和危险动作的决策点给出准确一句话，而不是全站删术语。

情绪上的主要低谷不是页面“不够温暖”，而是**我不知道它是否保存了、失败了、是否会发出去、是否删到原文件**。增加可信反馈比换口号、加吉祥物动画更有收益。

## 5. P1：优先处理的十项

### A01 — 知识库“不出本机”的承诺与远程处理路径矛盾

- **证据：O + S；领域：完整性/隐私沟通。**
- **位置**：`src/settings/KnowledgeRagPanel.tsx:69–76`；`src/chat/KnowledgeCenter.tsx:584–586`；`src/components/i18n.ts:2141`；`src-tauri/src/chat/knowledge_base/embeddings.rs:96–103`；`src/settings/DocumentProcessingPanel.tsx:83–92,180–186`。
- **问题**：副标题和横幅写“数据不出本机 / data never leaves your machine”，但 embedding 的请求体包含文档片段，发送到配置供应商的 `/embeddings`；用户还可选择第三方解析。供应商地址也可能是本机，缺陷是对所有配置作无条件本地承诺。
- **影响**：用户可能在错误的隐私预期下导入私人材料。这里不声称应用偷传、泄露密钥或实际发生了外传事故。
- **建议**：分别说明本地存储/索引、远程 embedding/重排、第三方解析；配置相关说明在导入/选择前可见。无需增加不存在的“完全离线”模式。
- **验收**：远程配置下不再出现绝对不出本机承诺；能识别处理对象与目的供应商；本机端点不被错误标为云端。符合 `PRODUCT.md:42` 的既有约束。
- **命令**：`/impeccable clarify`。

[界面证据：知识库 RAG 横幅](impeccable-audit-2026-10-10/knowledge-rag.webp)。该截图的 invoke 错误属于预览缺桥，不是隐私发现的依据。

### A02 — 笔记将未保存与保存失败显示为“已保存”

- **证据：S；领域：完整性/数据状态。**
- **位置**：`src/chat/NotesCenter.tsx:286–292,430–433,479–482`；`src/chat/notesDraftStore.ts:79–101,148–180`。
- **问题**：顶栏只有 `saving ? 保存中 : 已保存` 两档，而 store 还存在 pending/error。800ms 防抖期间及失败后都可能落到“已保存”；返回在 flush 失败时停留，但界面没有同步解释。
- **影响**：可见状态比落盘结果乐观。风险是用户相信内容已经持久化，不是本次已观察到数据丢失。
- **建议**：使用现有草稿状态显示未保存、保存中、已保存、失败；失败可宣布、可重试；受阻返回说明草稿仍在。参考已有自动化状态行，不再建立第二个保存负责人。
- **验收**：防抖前不是已保存；写盘拒绝后为失败且保留草稿；重试成功才显示已保存；返回保护仍有效。
- **命令**：`/impeccable harden`。

### A03 — 定时任务加载异常的终态与恢复入口仍不完整（部分修复）

- **证据：O（实际预览及原组件合成 IPC smoke）+ S；领域：状态/恢复；2026-10-10 已复查。**
- **位置**：`src/chat/scheduledTasks/useScheduledTasks.ts:94–101,149–150`；`src/chat/scheduledTasks/ScheduledTasksCenter.tsx:55,90–91`；`src/chat/scheduledTasks/ScheduledTaskEditor.tsx:44–56,78–79`。
- **已改进**：快照携带的 `error` 已进入共享状态，不再被无条件清空。后端定义文件不可读时的保护已补齐，详见第 11 节；该返回路径的剩余“错误+空库”归入 A04，而不是继续概括为所有失败都永久加载。
- **剩余问题**：首次订阅或 snapshot Promise 拒绝后仍保留 tasks=null，界面同时显示错误与加载中，没有页内重试。运行记录首次读取拒绝也同时显示错误与加载中；本次已打开原组件运行记录面板验证。
- **影响**：用户仍无法区分读取已失败与读取尚未完成。真实预览中的订阅失败由缺少原生桥接触发，不认定为原生程序桥接故障；合成 IPC 单独验证了 snapshot 拒绝时的界面分支。
- **建议**：首次传输失败显示失败及调用既有 refresh 的恢复动作；加载与失败互斥，旧快照保留。定义数据不可读是另一种不可写状态：遵从后端“修复文件后重启”语义，不能承诺普通刷新解除该保护。
- **验收**：首次 snapshot 或订阅拒绝后不再显示加载中；可恢复读取成功后进入真实空态/列表；运行记录采用相同终态语义；不破坏事件/快照先后保护及已有内容保留。
- **命令**：`/impeccable harden`。

[界面证据：读取错误与加载中同屏](impeccable-audit-2026-10-10/scheduled-load-failure.webp)。

### A04 — 多个列表把“读取失败”同时画成“成功空库”

## 7. 确认有效、应保留的设计与工程做法

1. **聊天主任务明确**：系统字体、墨色标题、居中输入、少量蓝强调符合用户确认的北极星。不因小字对比度问题把全界面变得喧闹。

3. **生命周期不是装饰**：安装任务、专家/笔记/自动化草稿有 session/revision/epoch 等过期结果隔离；应把正确状态画出来，而非删掉这些保护来“简化”。
4. **路由保活已处理隐藏交互**：当前 `ChatRouteKeepAlive.tsx:29–34` 是真实 hidden、aria-hidden、inert；不再沿用旧结构推断缓存输入框泄漏或抢点击。
5. **已有可靠模态实现**：AppDialog 与主题 JSON dialog 使用原生 showModal、名称、初始焦点和取消。复用比补每个手写遮罩便宜。
6. **自动化保存行可作现有正例**：`AutomationCenter.tsx:270–275` 明确未保存、保存中、保存失败·草稿保留及重试；不需要新建“保存状态系统”。
7. **所有权说明已有优秀样板**：媒体删除说明源文件、作品索引、导出副本与参考图影响；作品删除保留聊天/媒体源文件；笔记文件夹删除不删笔记。应复制语义清晰度，不复制代码。
8. **认证语义实事求是**：无 Key 端点与 OAuth 的就绪条件分开；空 Key 不等于伪造认证成功。
9. **性能架构有依据**：主要中心懒加载、笔记首次按需加载、消息历史虚拟化与 live row 分离、重内容延后渲染。不能仅凭文件大或没有 memo 判慢。

正常引导/设置表单因原生桥接不可用未打开。为补足控件证据，在 900 × 700 的临时浏览器页面中，通过 Vite 导入并渲染**现有 `Select` 原组件**，而非复制实现或 mock。组件后放置一个普通按钮，选项 A/B/C，只使用页面内 React state；未调用设置 API、写入存储或创建项目文件。

| 实际输入 | 观察结果 |
|---|---|
| 触发器上 Enter | 打开列表，焦点仍在触发器，值 A |
| ArrowDown → Enter | 未移动选项、未选中 B，列表仍打开，值 A |
| 第一次 Tab | 焦点到后续普通按钮，列表仍打开 |
| 第二次、第三次 Tab | 依次到选项 A、B |

### 8.5 已排除的错误结论

- **“neutral/zinc 固定浅灰、缺少 dark: 就不支持主题”**：错误。`src/index.css:42–99` 已映射到语义 token。

- **“Tauri invoke 报错证明桌面数据库坏了”**：错误。预览环境没有桥；只核实了现有 catch 后的界面分支。
- **“所有空数组都是用户没有数据”**：错误。尤其本次预览数据/不可用状态不能代表本机资料。
- **“没有 memo 或文件很长，因此页面很慢”**：没有运行证据，不立案。
- **“没有 h1/main 必然违反 WCAG”**：不能仅凭标签缺失作此判断；不列为本次 P1。

### 11.3 收尾顺序与本轮边界

定时任务不应再按“没有任何错误保护”处理。下一步只收尾：首次传输失败/运行记录失败的终态及恢复入口 → 定义数据不可用时隐藏成功空态、避免虚假的 0 和创建引导 → 明确删除任务与删除运行记录的范围。前两项不改变已补上的后端故障隔离、不可写保护和既有并发规则。
