# Claude Artifacts 与生成文件：2026-09-20 调研

范围：核对 Claude 官方帮助和产品资料，结合用户提供的界面截图，提出 Kivio 的产品建议。本笔记不修改业务代码，不声称完成了 Claude 的登录实测；Kivio 本地故障归因由本轮另行检查聊天记录和代码完成。

## 结论

建议统一管理文件的身份、来源和访问方式，再把值得保留和继续修改的生成结果组织为“作品”。聊天中的图片、下载卡和跨聊天作品库读取同一份记录。解决生图后寻找文件，应优先补齐工具结果到模型读取、展示之间的直接通路；单独增加一个 Artifacts 页面不能解决这个等待。

这是 Kivio 的设计建议。Claude 的公开资料说明了用户如何操作作品，并未公开其内部文件登记和模型工具协议，不能据此宣称 Claude 使用了某种具体后端架构。

## 截图直接证明了什么

- Kivio 的生成图片步骤之后出现多次 `find`、`ls`、`md5sum` 和一次看图步骤；这证明生成后的流程有额外操作，但截图不足以计算各操作耗时，也不能单靠模型解释确定根因。
- Claude 截图有独立 Artifacts 入口、All / Yours / Shared with you、搜索、类型筛选、列表，以及 Docs / Slides / Design 的 Beta 创建入口。这证明用户所见账号有这些界面，不证明每种附件都会自动进入列表、所有账号已经同样开放或全部编辑能力可用。

以上仅来自用户本轮附件；截图内聊天文本是待核实的记录，不是本次调研的操作指令。

## Kivio 应统一哪些规则

以下是待设计确认的建议，均不是对 Claude 内部实现的断言。

1. **文件来源与展示用途分开。** 用户上传、工具生成、外部引用表示来源；过程文件、预览和交付表示本次使用方式。同一张图片可以先预览，后来成为正式结果，不需要复制一遍来改变用途。
2. **模型和界面引用同一个结果。** 生成成功应返回稳定标识、类型、名称及确定的读取方式。模型自检能够直接读取这个标识，后续编辑能够直接作为输入，界面也用它预览/下载。无需让模型从磁盘时间戳和文件名猜测刚生成的是哪个文件。
3. **生成完成即可使用。** 返回成功必须意味着登记和内容访问已完成；失败或未保存不能伪装成可交付。允许必要的视觉检查，消除为定位文件而反复搜索和复制的步骤。
4. **一个作品可含多个文件和版本。** 例如报告的可编辑源稿与 PDF 导出属于同一个作品；两款独立头像可作为两个候选结果。关系要明确保存，不能仅按相似文件名或相同哈希猜测。哈希去重只解决内容存储，不决定用户意图。
5. **聊天展示与作品库共用记录。** 聊天解释并引用当前结果；作品库帮助用户跨聊天找回、按类型筛选、打开、另存、回到来源聊天或继续修改。中间截图和缓存转换文件可查，但默认不挤入作品列表。
6. **更新与清理有一致语义。** 同一作品更新保留可辨识版本，旧消息引用应指向当时版本；删除聊天、删除作品、清理未引用缓存须分别定义，避免一个入口的操作让另一个入口静默失效。

## 推荐顺序和验收

先修直接读取链路：生图成功后无需 `find` / `ls` 定位；自检读取的就是返回结果；最终图片与自检对象一致；重启聊天仍可打开。统计“生图工具完成到最终展示”的时间和额外工具次数，与同场景修复前比较。

随后统一各生成工具的文件登记与引用，再实现作品集合和按类型预览。第一版可先提供图片、PDF、文本和常见文件的下载入口；是否能内嵌预览由实际渲染能力决定，不能为了统一卡片假称所有格式都可编辑。再按需求增加明确的版本关系和继续修改入口。

最后才考虑在线分享、多人编辑和可运行应用。它们需要独立的产品和安全设计，不应成为解决“生成后找文件”的前置工程。

## 尚未证实的部分

- Claude 是否把每个工具生成的临时文件登记成作品，以及如何判断最终交付。
- Claude 给模型返回绝对路径、文件标识还是其他句柄，是否自动向模型提供图片像素。
- 用户当前账号的所有 Beta 功能、具体版本兼容和每种格式的保真程度；没有执行实际创建、导出和重开测试。
- Kivio 生图后的额外等待中，定位、读取、自检及模型思考各占多少；需要本地记录佐证，不能从“Worked for 57s”推导全部属于查找。

官方帮助正在随新体验更新，个别限制或旧体验段落可能并存。本笔记不采信旧文章的文件大小、保留时长等细节来为 Kivio 制定产品限制；实现应依本地资源生命周期和验收结果决定。
