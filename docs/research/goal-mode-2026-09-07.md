# Kivio Goal 模式调研与实现建议

调研日期：2026-09-07。范围：公开项目文档、Pi 部分源码和 Kivio 当前执行链路；未安装或实跑外部扩展，未修改应用代码。下文明确区分上游事实与 Kivio 设计建议。

## 结论

建议做一个会话级的持续执行能力：用户给出目标，Kivio 保存目标和验收条件，执行现有 agent，在一次运行完整收尾后决定继续、验收、等待或停止。

首版采用 **Pi 的显式完成工具与受控续跑机制，加上基于实际结果的验收**。第二个模型作为可选验收器后续加入；优先把持久化、取消、用量和恢复做好。

界面可以叫 Goal 模式，底层使用独立的 `GoalState`，与 Act / Plan / Orchestrate 的执行策略分开。这样将来可以组合 Goal + Orchestrate，而不需要继续扩展互斥模式枚举。

### Hermes：验收器需要实际证据

Hermes 的完成条件覆盖结果、验证、约束、范围和停止条件；质量检查命令失败时不进入 judge，而是把失败结果交回执行者。它还支持等待后台进程，减少重复催促。[官方目标文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/goals.md)

历史 issue 报告过两类问题：探索任务已经交付建议，却因缺少完成措辞被继续催促，导致任务范围扩大；judge 出错被当作 continue，导致重复发送完成消息。这些是历史案例，不代表当前版本仍未修复。[范围扩张案例](https://github.com/NousResearch/hermes-agent/issues/34196)、[重复续跑案例](https://github.com/NousResearch/hermes-agent/issues/27585)

因此 Kivio 的建议是：判断原始验收条件是否满足；judge 异常进入有限重试或暂停；避免用“没有说完成”推导“还有工作”。研究、文档、设计任务也要能完成，不能统一要求改代码或跑测试。

### 其他长时 agent 的启发

Anthropic 的实践指出仅靠上下文压缩仍会丢失任务状态或过早结束，使用结构化清单、增量执行和实际测试改善了这些问题。其后续实验也探索了 planner / generator / evaluator，但强调通过实验判断哪些组件必要。[2025 实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[2026 实践](https://www.anthropic.com/engineering/harness-design-long-running-apps)

Kivio 首版可借鉴清单、交接记录与验收方法；不必因此强制每个 Goal 都创建多个 agent。

## 建议的产品行为

1. 输入框提供 Goal 入口，也接受 `/goal <目标>`。输入清楚即可启动；含糊要求可先形成可编辑的验收条件，只有影响执行的关键缺项才提问。
2. 会话显示目标卡片：目标、已验证条件、当前动作、累计用量和暂停/继续。展示“已验证 2/4 项”，避免模型猜测百分比。
3. 普通插话按当前 steering / follow-up 规则送达；用户修改目标或验收条件时，增加目标版本并使旧判定失效。
4. Goal 期间的停止按钮立即停止自动续跑并取消当前 Goal 所属运行；保留已保存的进展，不回滚已经发生的文件或外部操作。
5. 等用户回答、工具审批或外部结果时显示明确等待原因，停止无意义的模型调用。
6. 默认维持原工具权限。切入 Plan 时暂停执行型 Goal；切换工作目录、外部运行时或会话历史分支时先暂停并重新绑定上下文。
7. 首版只为 Kivio Agent、单个主执行模型提供完整支持。外部 CLI 的原生 Goal 由相应适配器驱动；不要同时再套一个 Kivio 自动续跑循环。

## 建议的运行架构

```text
目标与验收条件持久化
          ↓
GoalRunner 取得当前目标版本与运行权
          ↓
现有 agent 完成一次运行（内部可有多个模型/工具轮）
          ↓
保存回答与用量 → 结束协议 run → 释放运行/发送槽位
          ↓
重新读取目标版本、用户输入、等待、取消和预算状态
          ↓
继续执行 / 验收 / 等待 / 暂停 / 完成
```

外层 `GoalRunner` 管跨运行调度；内层循环只增加必要的 Goal 上下文、结构化控制信号和模型调用前的预算检查。不能只在外层限制轮数，因为一个 run 内部就能发生大量模型调用。

不要把前端 `done` 事件、单个工具轮结束或模型 stop reason 当成 settled。当前 `finish_run` 调用时函数守卫仍可能存活，发送入口还可能持有 reservation。建议在全部相关资源释放后由后端统一调度，再原子争取下一轮资格。

### 数据和状态

建议新增会话级 `GoalState`，包括：

- `id`、`revision`、`conversation_id`、运行上下文标识；
- `objective`、验收条件、约束与范围；
- `status`、停止原因、最近进展摘要、证据引用和下一步；
- 总用量、自动运行/模型响应计数、停滞计数、可选预算；
- `active_run_id`、待续跑意图、等待来源与可选截止时间。

| 状态 | 语义 | 自动行为 |
| --- | --- | --- |
| active | 正在推进目标 | 收尾后符合条件才继续 |
| verifying | 正在核对完成证据 | 通过则完成；缺项回到执行 |
| waiting | 等待用户、审批或外部事件 | 只由匹配事件或有效定时器唤醒 |
| paused | 用户暂停、重启恢复或停滞保护 | 由用户继续 |
| blocked | 明确的不可自主解决条件 | 说明需要什么改变 |
| budget_exhausted | 达到用户设置的运行资源限制 | 调整限制后再继续 |
| completed | 当前目标版本的条件已满足 | 停止 |
| cancelled | 用户终止本目标 | 停止并保留记录 |

额度、鉴权、网络错误应保存结构化 reason；短暂错误先走既有重试，重试耗尽转等待或暂停。不要把所有失败都标成“目标卡住”。

### 完成工具与验收

建议提供 `get_goal`、`report_goal_progress`、`request_goal_completion`、`report_goal_blocker`、`wait_for_goal_event`；名字可以调整，关键是职责和权限。

`request_goal_completion` 仅提交完成候选，后端负责状态迁移。检查目标 id/version、待解决条件和证据；若配置了实际检查则通过既有工具执行器运行，并记录命令、环境、退出结果和对应工作版本。验收期间代码或目标改变，旧结果失效。子代理可汇报自己的结果，不能直接完成父 Goal。

首版使用“执行者逐项举证 + 后端检查证据引用与可执行验收项”。它仍不能保证自然语言需求全部满足；对难以机器验证的任务，界面应能区分模型自检与实际检查。

后续可以在提交完成候选、阶段验收或疑似停滞时调用辅助 judge。其输出建议为 `pass / continue / wait / blocked / unknown`，必须引用条件和证据。judge 不可用不算通过，也不应无限 continue。

模型不能自行降低验收条件来获得完成，也不能提高预算或绕过暂停。相关条件修改由用户操作，或由用户明确授权的修改工具完成。

### 防止重复与空转

- 续跑票据至少绑定 `goal_id + revision + previous_run_id`；旧回调、旧工具和旧定时器全部拒绝。
- 同一目标最多一个主运行和一个待执行续跑意图；用户输入优先，消费票据和登记运行权必须原子化。
- 阻塞次数由后端证据统计，不能相信模型填入的 `repeated_turns`。缺少明确凭据或用户决定可直接等待，不必强行失败三次。
- 重复空回答、相同失败命令、重复读同一材料且没有新证据可触发停滞保护；仅调用过工具不代表取得进展。研究任务的新来源和分析产物同样算进展。
- 后台操作用工具任务 id / run id 关联等待，避免仅依赖可能被复用的 PID。没有真实唤醒来源时只进入人工等待，不假装会自动恢复。
- 崩溃恢复时把未完成目标恢复为暂停，说明上次执行到哪里。Goal 检查点无法回滚文件系统或外部服务；遇到未确认的副作用先核对结果，不能盲目重放。

### 预算与上下文

累计成本应包含目标所属的模型执行、压缩、辅助验收，以及后续纳入支持的子代理；避免父子重复计算。没有 provider usage 时显示估算，不能宣传精确费用封顶。

执行前检查预算并限制下一次请求；运行中依据可用用量事件停止。工具已产生的效果不能撤销，流式用量也可能滞后，所以要说明预算的计量边界。恢复执行可以重置本次自动运行配额，不能抹掉历史总消耗。

Goal 的权威数据放在持久存储中；每轮注入短摘要，包含当前目标版本、剩余条件、进展和停止规则。压缩后从权威状态重建，不依赖压缩模型是否记住目标。变化频繁的计数放在靠后的运行上下文，避免频繁改写稳定的系统提示前缀。

## 首版实施顺序

1. **状态与协议**：在 Rust 定义 GoalState、命令与事件；沿用 repository 原子更新；同步生成 TypeScript/Schema，并覆盖旧会话默认值。
2. **后端调度**：新增 GoalRunner，复用 reply 入口；明确 settled、用户输入优先、取消和续跑票据；模型调用前加入预算检查。
3. **目标工具与验收**：接入已有工具注册、执行和权限流程；完成候选只在对应版本的证据通过后转 completed。
4. **界面**：Goal 入口、目标卡片、状态原因、暂停/继续；主窗口与弹出窗口一致；合并自动轮通知。
5. **恢复与验证**：保存目标进度与运行归属；覆盖异常路径，再决定是否扩展辅助 judge、Orchestrate 和外部 CLI。

建议新增模块为 `src-tauri/src/chat/goal/`，按 state / runner / tools / verification 划分；命令挂到现有 `chat/commands`。这些是建议路径，当前尚未创建。

首版验收重点：普通聊天行为保持稳定；需要多次执行的目标最终完成；用户停止后不会被旧回调重启；编辑目标后旧完成请求无效；压缩不丢目标；重启不静默开跑；等待不空转；验收失败不能 completed；多窗口不重复调度；实际用量缺失不会被显示成零；外部原生 Goal 不被双重调度。

后续增强优先级：可选 judge → 可靠外部事件等待 → Goal + Orchestrate 用量汇总 → 外部 CLI 能力适配。多目标队列、跨项目调度与无人值守重启应单独设计，首版无需一并承担。
