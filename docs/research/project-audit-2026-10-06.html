六项已确认的问题

P11. 请求调试承诺“不落盘”，实现却持续写盘

src/settings/RequestDebugPanel.tsx:694–695 的中英文说明都承诺仅内存保存；src-tauri/src/chat/request_debug.rs:46,50–59,276–289 会将缓冲写入应用数据目录的 request_debug/records.jsonl。

触发条件是用户开启请求调试。保存内容包含请求正文；请求记录构造仅专门剔除视频载荷，不能把“请求头 key 脱敏”理解为“正文内容无敏感信息”。没有发现凭此可断言远程泄露的证据，但本地持久化行为已违反界面契约。现有 Rust 测试明确验证落盘与手动清除，说明不能只靠测试绿灯发现这类矛盾。

建议：默认遵守内存记录承诺；若确需磁盘诊断，做成独立显式选项，说明位置、保存内容及清除方式，并对 URL、额外认证头、正文做分层处理。验收应覆盖默认无文件、显式开启后落盘、清除后文件消失，及失败时的可见反馈。

P12. 安装包对外发布早于包内资源验证

.github/workflows/release.yml:44 创建非 draft Release；:98–114 构建并上传，releaseDraft: false；直到 :116 与 :136 才解包验证 macOS/Windows 资源。

资源检查失败或某个平台构建失败时，已公开版本和资产可能仍可下载。建议使用 draft 暂存，两平台构建、资源校验及 portable 检查全部成功后，由最终 job 统一发布。对重跑已有 Release 的情况也要定义行为，避免再次暴露半成品。

P13. Release 没有绑定同一提交的完整质量门

.github/workflows/release.yml:52 只依赖 create-release；构建使用 npx tauri，其 beforeBuildCommand 仅执行 Vite。Release 工作流本身没有 lint、TypeScript、协议一致性、架构或前后端行为测试依赖。

这不代表主分支没有远端保护；本次未核查 branch protection。但工作流自身不能证明待发布 commit 已通过质量门，手动 ref 和 tag 构建尤其需要绑定验证。

建议：提取可复用 quality workflow，解析并固定待发布 SHA，使验证和打包使用相同 SHA，避免复制两套检查列表。

P24. 性能检查将缺失数据当作零成本

scripts/check-chat-performance-report.mjs:20–29 将缺失 samples、longTasks、buckets 替换为空数组；后续最大值与总计默认零。我实际给脚本输入 {}，它输出全零、空 violations，并以 0 退出。

探针未启用、采集失败、拿错文件时，也能出现“性能通过”。这与 docs/perf/chat-rendering-baseline.md 中“空生产 Profiler 报告不等于零成本”的说明不一致。

建议：先校验报告版本、场景与必要样本，缺失数据判为不可验收。不同采集模式分别定义必需字段；longTasks 为空可能完全正常，不能机械要求每个数组非空。再执行现有预算判断。

P25. Windows 平台回归发现过晚

.github/workflows/ci.yml:22 只在 macOS 执行质量 job，Windows 仅在 Release 矩阵出现。macOS 无法编译检查 Windows 条件分支，Windows 单测也不在这两个工作流中执行。

建议 PR 增加 Windows Rust 编译与平台相关测试；前端通用检查保持一次即可。这是已确认的覆盖缺口，不是已确认的 Windows 故障。

P26. 文档忽略规则覆盖了产品运行资源

.github/workflows/ci.yml:7,14 忽略所有 **.md 及 docs，而 src-tauri/tauri.conf.json 打包 skills、plugins 和 docs/licenses。仅修改或删除 SKILL.md、参考资料、许可证 Markdown 时，不会触发此 CI。

建议只忽略纯说明文档；对随包资源设置轻量资源检查，无须所有 Markdown 修改都执行完整 Rust 测试。验收样例应包含“仅删一个打包技能文件”能触发并阻断检查。

需要测量后决定的优化

渲染依赖与首次使用成本

本次构建的 minified chunk：ChatMarkdown 1551.25 kB、NotesCenter 1129.41 kB、Chat 1010.19 kB、ApprovalCard 691.47 kB。src/chat/ChatMarkdown.tsx:5–11 静态接入多种渲染插件，是适合分析的依赖入口。

这些名称不代表体积全部来自对应组件，gzip 体积也不等于桌面 WebView 的解析执行成本。项目已有 lazy 页面、重内容延迟挂载、虚拟列表与流式状态拆分，笔记也已有首次使用加载，应保留。

先固定 F1–F5 场景，测冷打开聊天、首次代码/图表渲染、长回复更新、会话切换的 p50/p95、长任务与内存。只有确认依赖加载阻塞后，再按真实模块归属延迟加载 Mermaid/语法能力；不以调高 chunk 警告阈值当优化。

对话库全文搜索的规模成本

src-tauri/src/chat/storage/search.rs:119–136,350–361 在元数据未命中时读取会话文件，必要时解析正文；对话库为计算 total 需筛选全部候选。后台线程与共享读屏障已经存在，因此不能说它必然阻塞 UI 或全局写锁。

建议用 100、1000、10000 条合成会话测搜索延迟、读取字节和快速连续查询。若不达预算，先考虑可重建的正文索引、查询取消或合并；保留原 JSON 为真源，避免未经测量就整体迁移数据库。

调试记录需要字节预算

request_debug.rs:50–59 每次复制最多 50 条记录并同步重写整个镜像；50 条是数量上限，不是总字节上限。请求正文含完整上下文或图像时，调试可能额外放大内存与 I/O 成本。

在修正落盘契约时一并建立每条/总量字节预算，保留诊断必要字段，按需导出完整内容。当前未测得实际延迟，按性能风险处理，不标为已复现卡顿。

与其他 Agent 客户端的对比

使用 Exa 的 3 组搜索共返回 14 条结果，再读取官方仓库、文档及 OpenCode 关键源码；不采用第三方汇总作为技术结论依据。以下为本次检索到的官方资料，不是四款软件在相同硬件上的实测排名。动态分支未固定 SHA，后续实施前需再次核对接口。

项目官方资料确认的特点Kivio 可借鉴的方向实施约束
AionUi内置 Agent 与外部 CLI 并存；ACP/兼容适配；明确各代理保留各自模型、认证、工具和权限能力。把运行时能力差异做得更易理解：用户能在使用前看见某个动作是否支持、为何不可用。Kivio 已有 supports_steering、supports_follow_up 等字段，应扩展已有能力真源，避免新增另一套前端判断。
OpenCode终端与桌面入口；独立 snapshot 模块提供 track、restore、revert、diff；压缩代码保护近期上下文并处理旧工具输出。任务结束后集中看变更、理解回退范围；对压缩效果建立可观察的验收样例。Kivio ADR-0006 的“回到这里”不撤销文件。若加入文件恢复，需独立动作、预览和冲突保护，先解决产品语义，不能静默改变既有行为。
GooseRecipes 将提示、扩展与设置组织为可复用工作流，并支持快捷启动与子配方。将已完成的有效流程保存为带输入参数的模板，降低重复任务的启动成本。Kivio 已有助手、技能、定时任务、自动化；优先在既有归属内组合，不创建第五种互相重叠的任务系统。
Cherry Studio多供应商、多模型对话、文档处理、翻译、WebDAV 备份等通用桌面工作能力。改善模型配置、历史资料、附件与备份的可发现性，缩短“配置好到第一次成功使用”的路径。这是产品建议，本次未做 Kivio 原生 UI 可用性测试，不能据此断言某个现有页面难用。

OpenCode 的实现依据：snapshot 源码、compaction 源码。其官方配置文档也指出快照可能增加大型仓库的索引耗时和磁盘占用，因此不能把“有快照”直接推成“更快、更省资源”。

定位建议：Kivio 值得继续强化“屏幕级操作 → 对话 → Agent 执行 → 查看交付物”的桌面闭环。多接一个 CLI 的收益取决于真实用户需求；现有多个运行时的稳定续聊、取消、错误解释和产物交付更值得优先投入。

应保留的设计与推荐落地顺序

应保留：导入原生会话的所有权与工作目录约束、历史快照差异提示、子代理身份跨任务保留、设置写入 CAS、会话原子写入、流式内容与低频状态拆分，以及运行中草稿追加日志。

特别核对了 src-tauri/src/chat/commands/messages.rs:534：工具轮间草稿已写 append-only journal，不能再依据旧注释提出“每轮整本重写会话”的问题。draft_journal.rs 已有 16 MiB 轮转逻辑，后续应围绕真实瓶颈做测量。

测试方面，设置多窗口冲突、真实 AppKit 红绿灯几何、安装包文件 hash 属于有价值的行为/平台契约；没有证据支持大规模删除测试。优先补齐“UI 承诺与后端行为一致”的验收。

  1. 第一批：修正信任边界。请求调试落盘契约、draft 发布与同 SHA 质量门、性能空报告拒绝。验收分别用真实文件存在性、故意失败的发布验证、空/非法/有效性能报告。
  2. 第二批：补齐交付覆盖。Windows PR 编译/测试、技能和许可证资源轻量门禁。复用现有检查器，保持规则单一维护。
  3. 第三批：建立性能基线。测量冷启动、F1–F5、全文搜索和开启调试时的成本；按最大的实测瓶颈逐项优化。
  4. 第四批：完善 Agent 体验。统一解释运行时能力与失败原因、改善产物查看，再评估模板化工作流和独立文件回退。

优先级说明：P1 建议下次正式发布前处理；P2 应安排近期迭代。产品建议与性能风险不等同于已确认缺陷。本次未修改或提交修复。
