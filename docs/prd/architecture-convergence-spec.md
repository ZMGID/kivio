# Kivio 架构收口：语义一致性、状态所有权与验收

状态：代码验收完成，平台实机验收待补（R1–R5 已实施；macOS 未验证，Windows T15 尚未实机执行）。基线：`dc1eb6cf`。日期：2026-09-19。

发布记录：[GitHub #52](https://github.com/ZMGID/kivio/issues/52)，标签：`ready-for-agent`。

本规格补充并纠正第一阶段《全项目架构整理规格》的完成判断。第一阶段结构整理已有成果，但设置、路由、状态所有权及架构检查仍有缺口；不是只剩跨平台冒烟。本文的实施决策优先于旧实施记录中的完成声明，原有产品不变量与 ADR 继续有效。

## Problem Statement

用户需要设置保存后与实际运行一致，切换页面后不被旧请求拉回，关闭并重开时恢复正确位置。当前项目已有领域目录、公开接口和部分状态 owner，但业务规则和生命周期仍分散；一次看似局部的修改仍可能造成跨窗口覆盖、异步串页或配置回退。

基线复核确认如下问题。这里的证据区分实际函数复现、源码时序判断与架构缺口；未执行实机复现的场景不得报告为实机通过。

| ID | 已确认的缺口 | 证据与影响 | 验收批次 |
|---|---|---|---|
| S1 | 设置编辑缓冲与已保存基线混用 | 后端规范化导致回包不同后，原始草稿被当成已保存基线；保留未填完输入与接受规范结果没有分开 | R1 |
| S2 | 接收外部设置后未推进合并基线 | 实际函数复现：收藏连续由空列表变为 `[one]`、`[one,two]`，第二次合并仍为 `[one]`；数组整段取舍会扩大覆盖范围 | R1 |
| S3 | CAS 不覆盖客户端读到提交的完整期间，且缺少统一跨窗口失效通知 | A/B 从同一旧值编辑，A 保存后 B 才进入后端锁，B 取得新 revision 却携带旧全量值，仍可覆盖 A；普通设置写入未统一广播 | R1 |
| N1 | 前后端恢复路由规则不一致 | Rust 接受 `chat/`、`chat/a/b`、`chat/%E0%A4%A`，前端拒绝；冷启动恢复与运行期导航分歧 | R2 |
| N2 | 部分导航异步分支未校验所属导航 | 等待弹出窗口列表后直接占据会话；进入中心页没有使旧加载失效，旧结果或旧错误可能改回会话 hash | R2 |
| N3 | 旧路由迁移在保存确认前删除源记录 | 底层持久化错误被吞掉，失败后既无原记录也无可靠重试依据；只影响恢复位置，不等同于会话文件丢失 | R2 |
| O1 | AppState 仍暴露可变领域状态与宽依赖 | 聊天 generation/replies/protocol、外部 CLI 会话及输入信箱仍可被跨域访问；存在封装缺口，不据此直接断言已有竞态 | R3 |
| O2 | 三个页面仍承担状态机和清理顺序 | Chat 协调路由与加载的循环依赖，Lens 手工重置捕获/消息/标注等状态，Settings 页面协调保存、合并与下载生命周期 | R4 |

## Solution

先修复设置与路由的可观察语义，再围绕这些行为收回状态写入和生命周期协调权。设置采用带版本的规范快照、独立编辑缓冲及冲突可见的提交过程；导航采用统一契约和导航代次，旧异步结果不能改变当前目标。随后让领域 Module 接管状态转换，让页面只连接用户意图、展示快照与生命周期入口，并使 CI 同时约束文件依赖和领域依赖。

保留已有 Ask User 契约、外部 CLI 代理策略、私有存储拆分、原子写入回滚和已成立的 Lens/MCP/Automation owner；仅在实现本规格所需的调用点调整它们。

## User Stories

1. 作为设置用户，我希望保存后显示的有效值与实际运行值一致，以便知道当前生效的配置。
2. 作为设置用户，我希望未填写完的 API key、请求头和模型输入仍保留，以便继续编辑。
3. 作为设置用户，我希望编辑占位行不会被误报为已持久化，以便正确理解保存状态。
4. 作为设置用户，我希望后端修正非法值后页面接纳规范值，以便避免反复提交无效配置。
5. 作为设置用户，我希望保存期间继续输入的内容保留，以便自动保存不吞字。
6. 作为多窗口用户，我希望分别修改无关字段时两项修改都生效，以便窗口之间不会互相覆盖。
7. 作为多窗口用户，我希望同一字段发生冲突时收到明确提示并保留草稿，以便自行选择最终值。
8. 作为设置用户，我希望连续收藏或开关更新按顺序进入页面，以便后一次更新不被自动保存撤销。
9. 作为设置用户，我希望一个供应商的编辑不覆盖另一个供应商的新配置，以便并行操作可靠。
10. 作为设置用户，我希望保存失败时保留编辑并可重试，以便错误不会伪装成成功。
11. 作为其他窗口的用户，我希望普通保存、收藏、插件和后端配置操作后及时读取新设置，以便界面与运行状态一致。
12. 作为聊天用户，我希望快速从对话 A 切到 B 后只展示 B，以便迟到请求不抢回页面。
13. 作为聊天用户，我希望进入设置或其他中心页后旧会话加载失败不会改动当前页面，以便导航稳定。
14. 作为弹出窗口用户，我希望窗口归属检查也遵循当前导航，以便旧占位结果不覆盖新目标。
15. 作为聊天用户，我希望前进、后退、旧链接与冷启动恢复使用一致路由规则，以便重开行为可预期。
16. 作为聊天用户，我希望损坏的路由安全回退且不进入恢复记录，以便既不崩溃也不反复恢复坏地址。
17. 作为升级用户，我希望旧恢复记录只在新存储确认成功后删除，以便失败后仍能重试。
18. 作为聊天用户，我希望切换视图不停止后台执行，而显式停止仍取消对应执行，以便保留既有运行语义。
19. 作为 Lens 用户，我希望关闭、重开、切换历史后旧捕获或旧回包不能污染新内容，以便截图与回答归属正确。
20. 作为维护者，我希望修改领域行为主要涉及所属 Module 与接口测试，以便减少跨文件连锁修改。
21. 作为维护者，我希望新增反向依赖与领域依赖环被 CI 阻止，以便公开目录不能掩盖职责倒置。
22. 作为验收者，我希望完成报告明确代码验收、自动验证和平台实机验证，以便不再把部分通过当成全部完成。

## Implementation Decisions

### D1：设置快照、编辑缓冲与提交版本

- Rust Settings Module 继续拥有持久设置的默认值、迁移与规范化权威。明确区分已确认规范快照、相对该快照的用户编辑、尚不能序列化为有效设置的 UI 占位输入；后两者不能充当已保存基线。
- 规范回包推进规范基线。保存期间没有新增编辑的持久字段采用回包值；新增编辑重放在新的规范基线上。占位行以独立编辑身份保留，不依赖伪造脏检查结果保留。
- 从后端接受外部快照时，原子更新规范基线与重基后的草稿；重基结果不能在下一次更新中被误判为用户刚做的编辑。
- 有稳定身份的供应商、MCP server 等集合按实体身份和编辑字段合并；明确区分实体删除与修改冲突。收藏按增删意图协调。不能把改动一个实体解释成覆盖整个集合；顺序本身有冲突时必须显式处理，不擅自排序。
- 设置读取、完整保存、导入和轻量写入形成带版本的快照契约。版本必须来自编辑所依据的读取，不能在提交排队之后重新取得当前版本并给旧草稿背书。后端原子验证 expected revision 后提交，所有规范值写入均推进同一版本序列。
- 版本冲突返回可识别的冲突结果。客户端刷新后仅在编辑互不冲突时有界重基重试；同字段冲突保留草稿、展示冲突且不假报保存成功。不允许用最新 revision 无条件重交旧全量对象。设置导入作为显式整体替换，也必须定义并校验其开始时的版本。
- 版本需能区分后端重启前后的快照，可使用进程 epoch 加序号等方式；不要求改变磁盘设置格式。命令调用方及回包解码同批迁移，旧调用不得成为不受保护的旁路。
- 成功提交后统一广播不含凭据的变更通知，携带可用于比较的版本身份；失败不广播成功。完整保存、导入、收藏、卡片宽度、插件、OAuth 和自配置等持久写入口全部列入核对；合法的仅内存更新须单独声明通知与持久化语义。
- 每个窗口的缓存接纳单调的新快照，乱序读取、保存回包或通知不能覆盖更新版本。订阅重建、窗口恢复和后端重启后重新取权威值，避免仅依赖一次通知产生永久旧缓存。
- 保留既有持久化失败恢复 store 缓存、外部 CLI 配置失败回滚以及迁移失败恢复行为；并发冲突也不能留下提前应用的运行时副作用。

### D2：统一路由契约与导航生命周期

- 路由分类、保留段、opaque ID 编解码和恢复合法性来自一个权威声明。沿用 Rust 到 TypeScript 的生成机制承载共享规则；各语言必要的解码实现受同一契约语料约束，不能各自维护保留段或允许名单。只增加两份相似测试不算消除双权威。
- 分开表达路由合法性、实时记忆策略、旧记录恢复策略。保留根路由可用于旧记录恢复但不被实时观察器主动记忆的现有差别；中心页、旧链接重定向、query、onboarding 和 popout 各自保持既有语义。
- 合法编码 ID 只按契约解码一次；非法百分号、非法 UTF-8、空 ID 和多段未知会话路径返回明确无效结果，不崩溃、不持久化，也不被当作新的有效导航目标。
- 由导航协调 Module 拥有当前目标和导航代次。对话、中心页、根页、旧链接重定向和弹出占位都经过同一导航入口；离开目标时立即使旧导航失效。
- 所有异步阶段在修改会话、hash、错误、loading 或恢复记录前验证导航身份，包括窗口归属查询、会话读取的成功/失败、后台刷新和渲染完成回调。后台刷新不得获得导航权限。取消导航只取消视图结果提交，不停止后台运行。
- 最近路由 Adapter 区分成功、失败和待重试，不在传输层吞掉需要由迁移处理的失败。迁移成功确认后才删除旧记录；失败保留源记录并允许重试。迟到的旧迁移完成不得覆盖更新的路由记忆或清除操作。

### D3：领域拥有可变状态

- AppState 保留为应用组合根与领域句柄集合。已有私有 owner 继续使用；优先把聊天运行控制、协议订阅、外部 CLI 运行会话和待输入信箱收回所属 Module。
- 对剩余公开可变字段建立迁移清单，覆盖缓存/探测、供应商 key 与能力状态、后台任务和调试记录。每项标明 owner、读写调用方、生命周期、锁顺序及迁移批次；不可只把裸锁搬到新的公开 struct。
- 每个状态只有一个可变 owner。领域实现通过所属句柄和窄操作接口工作，不能保留整个 AppState 作为任意跨域访问入口；跨领域行为在应用层组合。
- 保留多 run/generation、原子发送占位、按 run 自然结束与按对话取消的区别。明确资源创建、取消、等待回收、错误终态、退出与重启语义；禁止锁住同步状态后等待网络或子进程。
- 已迁移转发入口只可作为有明确删除批次的过渡。R3 完成时，清单中裸可变领域状态及其宽依赖均关闭；线程安全的不可变资源与领域句柄可以留在组合根。

### D4：页面 controller 接管生命周期

- Chat 的导航、会话加载和弹出归属由一个协调入口控制；输入/发送负责草稿、附件与提交，流式订阅负责执行归属和展示更新。页面无需通过赋值先后顺序或跨 hook ref 拼接循环依赖。
- Settings 编辑 controller 拥有规范快照、编辑缓冲、重基、自动保存、排队与关闭前 flush。OCR/更新下载、权限及记忆编辑等不同生命周期由各自 owner 负责，页面只组合其操作与视图。
- Lens controller 接管捕获、请求、历史切换与关闭重开的完整转换；沿用已有历史、请求和翻译 owner。页面可以保留局部布局与展示状态，但不能手工补齐领域重置清单或决定 owner 的清理顺序。
- 接口提供用户意图和可展示快照，不传入整页所有 setter，也不通过返回大量裸 ref 把状态机责任交回页面。无需追求特定文件行数或 hook 数；沿用现有 Interface，只有无法覆盖行为时才增加内部 Seam。

### D5：公共能力归属与架构检查

- 为 i18n、纯展示能力、传输契约和 normalizer 分配明确归属；领域无关能力不因历史目录位置成为另一领域的必需运行时依赖。公开 facade 可以保留，但必须有实际领域职责，不能作为穿透内部实现的通道。
- 依赖方向为应用组合层到领域公开 Interface，再到基础能力与 Adapter。基础 Adapter 不运行时依赖 feature 实现；必要领域协作采用单向依赖或由应用层协调。
- 保留文件图校验，并增加按声明的逻辑 Module 聚合后的依赖图校验。Adapter 节点不能被当作断路点；type-only 与运行时边可分别展示，但本规格两类均纳入架构约束。
- 跨领域聚合环即使没有文件级环也必须被发现。组合根只豁免合法挂载，不豁免领域间反向依赖。逻辑 Module 映射需有职责依据，禁止通过改分组或加 public 转发消除报警。
- 迁移期间例外必须有精确边、原因和移除批次；不得新增通配豁免。最终文件图和 Module 图均无临时例外。CI 同时验证生成契约没有漂移。

### D6：分批交付与完成定义

| 批次 | 工作 | 完成条件 | 依赖 |
|---|---|---|---|
| R1 设置一致性 | D1，关闭 S1–S3 | 规范回包、连续更新、跨窗口并发、通知及失败恢复通过行为测试；无无版本全量写旁路 | 无 |
| R2 路由语义与竞态 | D2，关闭 N1–N3 | 跨端语料一致；所有导航分支隔离迟到结果；迁移失败可重试 | R1 后实施，代码边界独立时可先补失败用例 |
| R3 后端所有权 | D3，关闭 O1 | 字段迁移清单闭环；窄接口与取消/并发/退出行为验证完成 | R1、R2 |
| R4 页面 controller | D4，关闭 O2 | 三页面只组合领域操作；controller 接口测试覆盖顺序和清理，无调用方补偿 | R1–R3 |
| R5 依赖与验收 | D5，关闭 G1 | 双层依赖门禁、生成检查、完整回归、平台矩阵与文档核对通过 | R1–R4 |

每批记录旧入口、新 owner、调用方迁移、删除的重复规则、失败用例及复验结果。迁移中的代码可以临时有适配层，但不得以过渡状态宣称整期完成。没有完成平台实机项时最多标记“代码验收完成，平台验收待补”，不能标记整体完成。

## Testing Decisions

优先测试用户操作所经过的现有外部 Interface：设置读取/修改/保存及订阅，导航/恢复和会话展示，以及领域的启动/取消/终态操作。复用现有缓存、设置重基、路由 hook、Lens 协调、Rust 设置事务与运行状态测试基础。新增 controller 测试应替代脆弱的内部细节断言，而非仅证明函数被调用。

| 验收 ID | 行为场景 | 必须观察的结果 |
|---|---|---|
| T1 | 规范化修正有效字段，同时存在未填完的 key/header/model 输入 | 有效字段采用 canonical 回包，占位输入保留；基线准确，不产生保存循环 |
| T2 | 保存期间继续编辑；成功、失败、关闭 flush 分别到达 | 新输入保留；失败可重试且不假报成功；没有遗漏的待保存编辑 |
| T3 | 连续外部收藏从空列表到一项再到两项 | 两次更新均进入基线与草稿，后续自动保存不回退第二项 |
| T4 | 外部更新与本地修改不同实体、同实体不同字段、同字段及删除交错 | 无冲突修改均保留；真实冲突可见，不整段覆盖数组 |
| T5 | 两窗口从同版本读出，A 先保存，B 在 A 后获后端锁 | B 的旧全量提交不能成功覆盖 A；非冲突重基可成功，同字段冲突保留草稿 |
| T6 | 普通保存、轻量写、OAuth、插件、自配置；读取与通知乱序/遗漏后重新激活 | 各窗口最终读取最新规范快照，旧回包不回退缓存；通知无凭据 |
| T7 | 持久化失败、CLI 配置应用失败、CAS 冲突、后端重启 | 内存/持久化/运行时按既有规则恢复；旧 epoch 请求不被接受；无成功通知 |
| T8 | 跨语言同一组根页/中心页/旧链接/query/encoded ID/坏编码/未知多段路径 | 分类、解码、可恢复性一致；实时记忆与旧根页恢复的策略差别明确 |
| T9 | A 的弹出归属查询迟到，用户已导航 B | A 不写 hash、不替换 B、不结束 B 的加载状态 |
| T10 | 加载不存在的 A 后进入设置/中心页，A 随后失败 | 当前页不被切回聊天；旧错误不修改新目标与其恢复记录 |
| T11 | 路由迁移保存失败、重试成功，以及迁移期间导航/清除 | 失败保留旧源；成功才清理；旧完成不能复活过期记录 |
| T12 | 并行 run、重复发送、按 run 完成、显式取消对话、窗口卸载 | 原子占位与执行归属不变；卸载不停止后台；资源按 owner 正确释放 |
| T13 | Lens done 先于最终回包，随后切历史、关闭重开或取消 | 当前错误可见，旧错误/捕获/回包不能污染新内容；不重复取消 |
| T14 | 跨 Module 双向边分布在不同文件，含 Adapter、barrel、alias 与 type-only 路径 | 即使文件图无环也报模块依赖环；合法单向依赖及组合挂载通过 |
| T15 | Windows/macOS 的热键、窗口恢复、捕获、后台进程退出及页面视觉 | 按平台实机记录结果；维持既有行为，未执行的平台明确未验证 |

时序测试使用可控 Promise、事件与同步屏障构造确定性先后，不依赖碰巧出现的真实延迟。跨窗口并发测试必须穿过提交版本验证，单测后端操作内部 CAS 不能替代 T5。以 UI/公开快照的最终值及持久化结果验收，不只测重基 helper。

实施前先为已确认缺陷建立失败用例。分批运行受影响测试；最终执行现有 lint、类型与协议生成检查、架构门禁、完整前端和 Rust 测试、生产构建以及涉及的平台打包检查。若本地二进制被占用，使用隔离构建输出或在可用环境补跑；library 通过不冒充二进制目标通过。忽略的认证 CLI 测试与人工冒烟单列记录。
