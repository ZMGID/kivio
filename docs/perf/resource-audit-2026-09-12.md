- 尚未用真实用户数据测量整个进程树 RSS/CPU，JS 字节和测试中的读取量不能换算成整机内存收益。

保留聊天与设置路由保活，以维持阅读位置和切换体验；中心页代码恢复后台提前加载。MCP 首次实际使用仍会承担按需连接成本，和页面加载策略分别处理。

MCP 冷启动还复现了一个必须随优化修正的边界：初始化延迟 3.2 秒的正常服务，在旧 3 秒发现预算下会首轮缺工具。无匹配缓存时现改用现有握手 30 秒 + 工具发现 30 秒的总预算，实际失败会提前返回；有匹配缓存时仍保持 3 秒后回退。各服务并行发现，不串行累加预算。这意味着首次使用配置错误的无缓存服务可能等待更久，但不会为了减少待机占用而在 3 秒时把正常冷启动误判成不可用。

结论：保留目标恢复的历史扫描优化、Git 查询合并及后台任务共享；页面代码加载恢复原策略。资源节省以不牺牲实际操作流畅性为约束，不能依赖用户提前悬停来抵消首次加载成本。

## 主要发现

### 1. 高优先级：启动恢复 Goal 会将全部历史会话同时读入内存

- `src-tauri/src/lib.rs:384` 每次启动调用 `pause_unfinished_after_restart`。
- `src-tauri/src/chat/goal.rs:581` 通过 `bulk_mutate` 查找运行中的目标，没有目标的会话也参与扫描。
- `src-tauri/src/chat/repository.rs:418` 的 `bulk_mutate_loaded` 持有全局独占 barrier 和索引锁，逐个读取索引中的完整会话，全部放进 `Vec` 后才执行筛选。

影响：即使用户从未使用目标模式，启动峰值内存和读盘成本仍随全部历史正文增长；需要同一 barrier 的会话操作会等待。后台 spawn 并不能消除内存和锁竞争。这是代码可确认的成本，具体耗时未实测。

建议：单独维护待恢复目标的会话 ID，只恢复这些会话；旧数据迁移逐条读取和释放，避免同时持有所有正文。保留重启暂停的语义。

### 2. 高优先级：普通聊天主动加载大量未使用功能

- `src/chat/Chat.tsx:1585` 空闲回调主动 import 设置、专家、技能、MCP、知识库、笔记、自动化和消息列表，超时参数为 400ms；这是模块加载与执行，不只是下载提示，也不意味着一定恰好在第 400ms 运行。
- `src/chat/Chat.tsx:126` 静态导入 RightDock；`src/chat/dock/RightDock.tsx:7` 静态导入所有面板。
- `src/chat/dock/TerminalPanel.tsx:7` 静态导入 xterm、fit、WebGL；`FileTreePanel.tsx:51` 又静态导入 ChatMarkdown。

影响：中心页面虽使用 React.lazy，仍会在打开聊天后提前加载；关闭 Dock 也不能省去其代码加载。终端进程本身已按首次选择终端页才创建，不能把代码提前加载误报为终端一直在运行。

建议：保留首屏必需加载，其余按实际导航或悬停意图预取；终端和文件预览拆成动态导入。优先调整加载策略，无须先删笔记、知识库或自动化。

### 3. 中优先级：Git 徽标重复执行状态与差异扫描

- `src/chat/dock/GitStatusPill.tsx:19` 与 `GitDiffChip.tsx:14` 各自实例化 `useGitBadge`。
- `src/chat/dock/useGitBadge.ts:44` 每次 refresh 先 gitStatus，再 gitDiffStat；分支徽标不消费 diffStat 但照样计算。
- `src-tauri/src/dock/git.rs:1260` 的 `git_diff_stat_sync` 内部再次调用 `git_status_sync`，之后执行 numstat，并为未跟踪文件计算行数。

两个徽标同时挂载时，一轮刷新可产生四次完整状态查询、两次差异统计，尚未计 Git 面板。文件事件会触发刷新，前端未做进行中请求合并；大仓库或 agent 连续写文件时影响更明显。后端已有文件事件去抖，不能将每次文件写入等同于一次完整刷新。

建议：按工作目录共享查询缓存和进行中请求；将状态与差异结果一次计算、共享给多个界面；只显示分支时避免差异统计。

### 4. 中优先级：MCP 默认提前连接已启用服务

- `src-tauri/src/lib.rs:481` 附近启动预热所有符合条件的已启用 MCP，并发上限 2。
- `src/chat/Chat.tsx:1578` 开聊天也触发 warmup；连接池单飞会复用连接，不能据此认定同一服务启动两份进程。
- stdio 空闲回收默认 10 分钟，每 60 秒扫描；HTTP 会话保持连接并 ping。

影响：启用本地 MCP 时，即使没有调用，也可能提前启动 Node/Python 等子进程。实际占用取决于服务实现，当前未测量子进程内存。

建议：提供按首次调用连接的省内存策略，将预热限制为用户常用服务。

### 5. 低至中优先级：页面保活和任务轮询可进一步收敛

- `src/chat/ChatRouteKeepAlive.tsx:15` 保留聊天与设置两棵树，用 display:none 隐藏。打开过设置后其组件状态仍驻留；隐藏不等于卸载。这是切换速度与内存的取舍，不是已证实的泄漏。
- `src/chat/BackgroundJobsIndicator.tsx:8` 和 `src/chat/dock/BackgroundTasksPanel.tsx:10` 都按 2.5 秒查询同一会话任务。任务面板展开时重复查询；指示器即使任务为空也继续查。两者已有 document.hidden 判断。

建议：共享任务数据订阅；无任务时退避或等待事件；设置页根据资源偏好卸载或限时保留。

## 不建议优先删除的功能

- 视频：`src-tauri/src/chat/video.rs` 发送时读取，总视频上限 14 MiB、请求上限 20 MiB；base64 对 14 MiB 数据约膨胀到 18.7 MiB，构造请求仍会产生临时分配，但没有证据表明它增加待机常驻视频数据。
- 自动化：调度器按下次触发时间休眠，无启用计划时最长每小时自愈一次，并非每秒扫描；运行工作流时的模型和工具成本另算。
- OCR：客户端构造不等于加载推理模型，worker 按调用运行。
- 模型目录更新主要是静态元数据，未看到由此新增后台轮询。
- TanStack 与 virtua 都有实际用途：前者用于消息列表，后者用于 Dock 文件/Git 列表；不能仅凭存在两套虚拟列表依赖就删除一套。
- 现有优化应保留：会话列表避免解析全部正文、打开会话单次读取、消息虚拟化、附件外置、外部 CLI 空闲回收、聊天窗口默认关闭销毁。

建议实施顺序：目标恢复扫描 → 页面/终端按需加载 → Git 查询共享 → MCP 按需连接 → 页面保活与任务轮询。修复后再用同一 release 版本、同一数据集，对比托盘待机、聊天空闲、长历史、频繁文件变更、视频发送五种场景，并统计整个进程树。
