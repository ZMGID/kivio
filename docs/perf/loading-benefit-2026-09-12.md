# 页面加载策略：资源收益与首次打开成本

最终决策：用户明确要求资源优化不能损害即时点击的流畅性，悬停 150 ms 不符合实际操作习惯。已撤回纯按需及悬停预热策略，恢复 Chat 开窗后的原有空闲页面预取和 Dock 静态导入；终端仍在实际打开时才创建 PTY，保留折叠状态不误启动的修复。下文为历史试验数据，不能将其约 6.6 MiB 初始堆节省作为当前实现的收益。

恢复后验证：前端全套 195 文件、1506 项通过；TypeScript、触及文件 ESLint、正式前端构建及差异空白检查通过。Dock 测试改为验证无需悬停即可同步显示已打开面板，并继续覆盖折叠时不启动终端、切换后的状态保留。Sidebar 的悬停回调和专用测试已移除。

## 本机结果

AMD Ryzen 7 7745HX，16 逻辑线程，约 16 GiB 内存，Windows 11，Headless Chrome 152。下表为生产构建、固定数据、正常 CPU 速度下的中位数。每个页面/策略重复 5 次；首屏和初始堆每策略汇总 15 次。

| 指标 | 原提前加载 | 纯按需加载 | 悬停预热试验 |
|---|---:|---:|---:|
| 聊天输入区首屏显示 | 210.5 ms | 162.8 ms | 162.8 ms |
| 未使用其他功能时的 JS 堆，GC 后 | 12.39 MiB | 5.74 MiB | 5.75 MiB |
| 输入框出现后 2 秒内已加载 JS | 5,886,642 B | 1,421,659 B | 1,421,932 B |
| 采样时累计主线程任务耗时 | 307.09 ms | 259.58 ms | 261.24 ms |
| 设置首次点击至内容显示 | 43.9 ms | 100.9 ms | 42.9 ms |
| 笔记首次点击至内容显示 | 14.9 ms | 57.0 ms | 13.4 ms |
| 终端代码首次加载并显示占位内容 | 9.7 ms | 25.6 ms | 10.4 ms |
| 设置再次打开 | 7.5 ms | 7.7 ms | 7.3 ms |

**悬停试验方案的首次点击数据有明确条件：点击前在目标入口悬停 150 ms。** 这段时间用于提前加载，并未计入点击后的等待，也不是总交互耗时减少了 150 ms。该条件验证用户有提前意图时可以隐藏加载成本；直接快捷键、触屏或无停留点击仍可能承担冷加载。

本机测得的初始收益约为 6.64 MiB JS 堆、47.7 ms 首屏时间。之前的“减少约 60%”指初始静态 JS 依赖字节；本表加载字节还包含原来的空闲预取。二者都不能解释为整个桌面应用性能或内存改善相同比例。

## CPU 降速验证

使用 CDP 设置 4 倍 CPU 降速，其他条件相同。它用于放大 CPU 开销，不能等同于某一款真实低配电脑。

| 指标 | 原提前加载 | 纯按需加载 | 悬停预热试验，悬停 150 ms |
|---|---:|---:|---:|
| 聊天首屏 | 845.0 ms | 730.6 ms | 721.6 ms |
| 初始 JS 堆 | 12.39 MiB | 5.69 MiB | 5.69 MiB |
| 设置首次显示 | 228.6 ms | 341.6 ms | 224.0 ms |
| 笔记首次显示 | 87.6 ms | 162.9 ms | 74.6 ms |
| 终端代码加载与占位显示 | 22.6 ms | 68.1 ms | 25.2 ms |

设置的 5 次首开区间：原提前加载 224.6–236.7 ms，纯按需 335.1–393.4 ms，入口预热 221.2–230.9 ms。纯按需的首次等待回退稳定可见；入口预热后的微小差异不解释为组件渲染本身变快。

## 历史试验实现（现已撤回）

- `Chat.tsx` 将页面加载函数集中为 `chatPageLoaders`，供 React.lazy 和入口预热共用。打开聊天时仍不批量导入中心页。
- `Sidebar.tsx` 在设置按钮和具体扩展入口收到 pointer enter / focus 时请求对应页面预热。展开“扩展”菜单本身不预热所有项目。
- `RightDock.tsx` 同样在具体标签悬停/聚焦时预热代码；首次真正打开才挂载面板，终端 PTY 仍在挂载后创建。之后保留已有终端、搜索和预览状态。
- 预热失败不会形成未处理的 Promise rejection；实际打开仍走原有懒加载/错误处理流程。

收益主要发生在刚打开聊天、尚未使用这些功能时。预热后的模块会在本窗口保留；用到更多页面后，内存差距会缩小。例如悬停试验方案首次打开设置后，正常 CPU 样本的 JS 堆约 9.79 MiB，原提前加载样本约 13.12 MiB。没有新增定时轮询或后台预热整个功能集合。

## 方法、限制与复现

在同一份工作区代码上隔离构建，仅改变加载策略。原提前加载通过恢复 `1ace9b62` 的 RightDock 和 Chat 空闲导入集合得到，其他性能修复保留一致。正式结果共 90 次独立浏览器上下文：3 策略 × 2 CPU 档位 × 3 页面 × 5 次。旧/纯按需交替执行，悬停试验方案单独成批验证；构建和测试进程均在计时前结束。没有使用网络降速。

首屏记录输入区挂载后的两次 requestAnimationFrame；点击记录捕获到 click 事件至目标实际内容出现后的两次 requestAnimationFrame。JS 字节来自 Resource Timing，堆来自 `HeapProfiler.collectGarbage` 后的 `Runtime.getHeapUsage.usedSize`，任务耗时来自 `Performance.getMetrics`。

使用固定设置数据和本机 HTTP 静态服务，文件系统页缓存已热，浏览器上下文各自新建。该试验衡量前端代码加载、保留和显示开销：不含 Rust 启动、WebView2 整进程 RSS、真实历史数据、后端 IPC 及 PTY 创建。浏览器无原生事件桥，存在两组共同的事件订阅错误，页面主体仍成功渲染。终端只验证代码成本，不能用其毫秒数宣称真实终端已经可输入。

本机复现与原始产物保存在被 Git 忽略的 `output/playwright/loading-benefit/`，目录明确作为测量工装，不进入产品。`result-1/4-1..5.json` 是旧/纯按需正式样本，`result-1/4-20..24.json` 是悬停试验方案样本；`summary.json` 汇总中位数及区间。0 和 10 号是预实验，未计入正式结果。目录中的产物对应历史冻结构建。构建工装面向当时的源码快照；当前已恢复提前加载，复测历史三组时应直接使用冻结产物，不重新构建。
